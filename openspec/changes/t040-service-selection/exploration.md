## Approaches

1. **A — RSC direct fetch + client selector islands with URL as source of truth (RECOMMENDED, mirrors T-039)**
   - `page.tsx` is async RSC: `const session = await auth(); if(!session) redirect('/login')` (inherits `(customer)` guard — no extra wiring). Then `const dtos = await listServices(db,{includeInactive:false})` directly (no HTTP hop, same D1 as T-039 `listVehiclesByCustomer`). Map `toJson(dto)` (`createdAt.toISOString()`, `updatedAt.toISOString()`) → `ServiceDTOJson[]`. Pass `initialServices` + `selectedId = searchParams?.serviceId` (validated UUID) to `<ServiceSelector initialServices={services} selectedId={selectedId} />`. `ServiceSelector` is `"use client"` compound reading `useSearchParams` and calling `router.push(\`?serviceId=${id}\`, {scroll:false})` on selection; displays `ServiceList` + `SelectedBanner` with `Continue` link preserving `?serviceId=` for T-041.
   - Pros: FCP fastest (SSR, `server-parallel-fetching`, streamed Suspense), no client `customerId` discovery problem, DTO serialized once (vercel `server-serialization`/`server-cache-react`), `selection` survives refresh/deep-link/share (URL canonical), T-041/T-042 can-statically read `searchParams` server-side without context hydration, auth resolved server-side (T-051 aligned), CSS/module + test harness reuse verbatim, DTO leak impossible (mapper single source), no `localStorage`/`context` expiry.
   - Cons: Two-step mental model (RSC shell + client islands) vs pure client, requires `searchParams` validation (UUID) in RSC and `router.push` in client; `db` direct call duplicates the thin `GET /api/services` handler logic (but T-039 already accepted this for `vehicles`, so precedent exists). Minor extra file `ServiceDTOJson` type.
   - Effort: **Medium** — establishes second FASE 8 screen reusing T-039 scaffolding, directly chains to T-041.

2. **B — Full client fetch via `GET /api/services` (`credentials:"include"`)**
   - `page.tsx` is `"use client"`; `useEffect` + `fetch('/api/services')` loads `ServiceDTOJson[]`; selection kept in `useState<ServiceDTO| null>` or `useContext`; `Continue` navigates with `state` or `localStorage.setItem('serviceId', id)`.
   - Pros: Simplest to reason about (no RSC boundary), zero server `db` import in page, trivial loading/error with `useState`.
   - Cons: **Anti-pattern per `vercel-react-best-practices`** (`client-swr-dedup` missed, waterfalls, extra round-trip before first paint, no SSR SEO, larger bundle if validators pulled client-side, `rendering-content-visibility` irrelevant). Public endpoint still pays 401→login mapping client-side without RSC redirect. Selection in `useState`/`localStorage` is lost on refresh or not deep-linkable, breaking T-041/T-042 contract (T-042 expects `?serviceId=`). Duplicates error handling already solved in A. Creates throwaway architecture T-040 would need to replace for T-041 chain.
   - Effort: **Low initial, High debt** — fastest demo, worst foundation for `T-041→T-043`.

3. **C — Server Actions (`"use server"` selection handler)**
   - Catalog still RSC `listServices(db)`; selection posts to a Server Action `selectService(formData)` that validates `serviceId` UUID + `activo==true` (re-fetches `getServiceById`) then `redirect('/appointments/new?serviceId=…')`. Optional progressive enhancement without JS.
   - Pros: No client JS required for selection, server-side validation of `serviceId` before navigation, leverages React 19 `useActionState`/`useFormStatus`, cleanest guard against tampered `serviceId`.
   - Cons: **Bypasses HTTP contract as source of truth** if action doesn't also call `GET /api/services` JSON (DT-03: other clients — mobile, external — rely on API boundary). Selection UX becomes full page POST vs instant `aria-pressed` toggle. Harder to show inline `durationMinutes` formatting/selected ring without client state. Testing Server Actions needs Next experimental utils, not covered by current `vitest` `jsdom` harness. Adds a route that T-041 already covers with `searchParams`.
   - Effort: **Medium** — elegant but unnecessary indirection for read-only selection; only justified if T-040 must be JS-disabled resilient (not in spec).

## Recommendation

**Approach A (RSC server-direct `listServices(db)` + client islands `ServiceSelector` with `?serviceId=` URL)** — same D1 as T-039, adapted because services don't need `customerId`.

- Aligns with `Technical-spec §8.1/§9` + `AGENTS.md INV-03/INV-08`: UI *may* call `GET /api/services` JSON (public active-only) but RSC skips the hop and maps via `toServicioDTO` so snake/Spanish never leaks. Client islands use `lib/api/services.ts` thin helper only for admin `includeInactive` refresh or future `T-042` fetch — not for initial list. `serviceId` stored in URL search params (canonical for chain), not context/localStorage, per `vercel-react-best-practices` `server-serialization` + `server-parallel-fetching` + `async-suspense-boundaries`.
- **Route:** `src/app/(customer)/services/page.tsx` (route group `(customer)` so `layout.tsx` guard applies; no URL `customerId`). Alternative alias `src/app/(customer)/appointments/new/page.tsx` that *re-exports* `src/app/(customer)/services/page.tsx` or redirects, so booking entry point reads naturally as `/appointments/new?serviceId=` while catalog remains `/services`. Proposal must lock one canonical path + one alias redirect to avoid duplication.
- **Component decomposition (vercel-composition-patterns):** Avoid `<ServiceCard selected disabled loading …>` boolean bloat; use **compound + explicit variants**:
  - `ServiceProvider` (optional; only if global selection needed) exposing `{services, selectedId, select}` via `createContext` + `use()` (React 19) (`state-lift-state`, `state-context-interface`), otherwise stateless `ServiceSelector` with `ServiceSelector.List`/`ServiceSelector.Card`/`ServiceSelector.SelectedBanner` (`architecture-compound-components`, `patterns-children-over-render-props`).
  - `ServiceList` iterates `ServiceDTOJson[]` ASC, `key={s.id}` (stable UUID), `ServiceCard` is presentational (`name`, `description`, `durationMinutes` via `formatDuration`), selected ring via `.cardSelected` not prop.
  - `SelectedBanner` only renders when `selectedId` matches a live `active` service; CTA `<Link href={/appointments/new?serviceId=selectedId}>Continue</Link>` or `/availability?serviceId=` per T-041 design.
- **Data-fetching (vercel-react-best-practices):** RSC list wrapped in file-convention `loading.tsx` Suspense (`aria-busy` + shimmer rows), `error.tsx` client boundary (`unauthorized→/login`, `forbidden→"Not owner"`, `other→retry`), `server-no-shared-module-state`, helper `src/lib/api/services.ts` with `credentials:"include"` for any client refetch. `page.tsx` passes only `ServiceDTOJson[]` (ISO strings) + `searchParams` — no `Date`.
- **Validation:** No create payload; just `z.string().uuid()` guard on `searchParams.serviceId` (extract to `src/lib/validators/service.ts` pure Zod) + `active` check (hide inactive per `T-016b`; if a tampered `serviceId` resolves to `activo=false`, show `INVALID_SERVICE` banner derived from `findServicioById` returning inactive). `durationMinutes` display via `formatDuration` (60→"60 min", 90→"1 h 30 min", 120→"2 h") — no client timezone math.
- **Why not B/C:** B breaks URL-driven chain and pays perf/debt cost flagged above; C adds Server Action indirection for a read-only action that URL already solves. A is the only option both spec-compliant (exercises T-017 contract without violating DT-03) and chain-proof for `T-041(c)→T-042→T-043`.

## Risks

- **Activo filtering leak:** `GET /api/services` default `activeOnly=true`; RSC `listServices(db,{includeInactive:false})` hides `activo=false`. If proposal accidentally uses `includeInactive=true` without admin gate, inactive services become selectable and `POST /api/appointments` will reject with `INVALID_SERVICE` (H-13 smoke). Verify `route.test.ts` expectation `listServicesMock({includeInactive:false})` + mapper test `active:false` triangulation.
- **Duration display vs overfetch:** `durationMinutes` is 30–120 %5 per `serviceCreateSchema` (Zod) and DB CHECK `duracionMinutos %5=0`; display must not recompute it. If UI fetches per-card `getServiceById`, it overfetches N+1. Fix: render from single `listServices` payload and derive `durationMinutes` by `find` on id; do not re-fetch.
- **Selection persistence across T-041 navigation:** Context-only or `localStorage` state is lost on refresh and not bookmarkable. Using `?serviceId=` solves it but requires URL validation (UUID + active) on every RSC load; otherwise tampered `?serviceId=garbage` would render broken `SelectedBanner`. Mitigate with `z.string().uuid().safeParse` + `find(active)` fallback to "select a service" empty state.
- **Styling debt second UI:** T-039 set semantic tokens in `globals.css` + `vehicles.module.css`; a second `services.module.css` that hardcodes colors or reimplements `.card` differently will drift. Mitigate by reusing token names (`--color-border`, `--space-*`, `--radius-md`) and extracting a shared `src/app/(customer)/_components/ui/card.module.css` if duplication exceeds ~30 lines (proposal decision).
- **DTO leak `nombre→name`:** `ServicioDTO` renames `nombre→name`, `descripcion→description`, `duracionMinutos→durationMinutes`, `activo→active`. Any direct `row.nombre` exposure in page or helper violates INV-08 and breaks `page.test.tsx` assertion `not toHaveProperty('nombre')`. Gate via mapper only.
- **Empty/loading/error states:** `listServices` returns `[]` not 404. UI must distinguish `[]` (show "No services available" empty state + no selector) vs loading skeleton vs `throw` → `error.tsx`. Missing `loading.tsx` file convention reverts to blank page during `auth()+listServices` await.
- **Route duplication ambiguity:** Creating both `/services` and `/appointments/new` as full pages duplicates the same list. Must decide canonical + redirect alias (e.g. `/services` canonical, `/appointments/new` redirects to `/services` if no `serviceId`, otherwise shows next step). Otherwise stale copy risk for T-041.
- **Test harness already present but mis-wired risk:** `vitest.config.ts` already has `jsdom` project for `**/_components/**` + `vitest.setup.ts` (`@testing-library/jest-dom`). If new service components are placed outside `_components/` or named without `.test.tsx` suffix, they fall into `node` project and `document is not defined`. Follow existing glob exactly.
